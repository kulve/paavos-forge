# Autonomous Paavo's Forge: Master Guidelines

## 1. Core Philosophy & State Management

This framework relies on strict isolation of concerns, explicit state management via Taskwarrior, and ephemeral Git branching to safely navigate LLM hallucinations and context limits.

### 1.1 State Tracking (Taskwarrior)
Do not use the file system (moving files between `dev/`, `fix/`, `prod/`) or unstructured comments to track state. State is tracked exclusively via Taskwarrior User-Defined Attributes (UDAs).

**Required Taskwarrior Configuration:**
```bash
task config uda.aiphase.type string
task config uda.aiphase.label "AI Pipeline Phase" # values: req, arch, test, impl
task config uda.aistate.type string
task config uda.aistate.label "AI Phase State"   # values: plan, write, review, done

```

* **Querying State:** The Coordinator uses JSON exports (`task status:pending +READY export`) to find the next actionable item.
* **Passing Context:** Subagents use Taskwarrior annotations *only* to link to file paths (e.g., `task <ID> annotate "Feedback: plan/arch-review/00001-rev.md"`), never for passing large text payloads.

### 1.2 Version Control (Ephemeral Branches)

Do not micro-commit to `main`, and do not leave artifacts uncommitted in a shared working tree.

* The Coordinator creates an ephemeral branch for each story: `git checkout -b story/00001-auth`.
* The Coordinator commits code locally *only after a phase passes review* (e.g., `git commit -am "phase(arch): 00001"`).
* **Rollbacks:** If the Implementation phase fails catastrophically, the Coordinator executes `git reset --hard HEAD` to revert the working tree to the clean Test phase.
* **Merging:** Once the story is fully implemented and passes system integration tests, the branch is squash-merged into `main`.

## 2. Top-Level Execution: The PM Loop

**Rule:** No Waterfall. Do not generate detailed story files for an entire milestone upfront.

1. **Milestone Definition:** The PM Agent writes `plan/milestones/XX-name.md`. This file contains only high-level epics, goals, and boundaries.
2. **Rolling Batch Generation:** The PM Agent reads the milestone file and current codebase, then generates only the **next 2 to 3 stories**.
3. **Task Seeding:** The PM Agent parses these stories and injects them into Taskwarrior with explicit dependencies.
4. **Execution:** The PM Agent pauses while the Coordinator loop processes the batch.
5. **Re-evaluation:** Once the batch is merged to `main`, the PM Agent wakes up, re-reads the codebase, checks off milestone goals, and generates the next 2-3 stories.

## 3. Artifact Definitions & Syntax

### 3.1 Stories (`plan/stories/0000X-name.md`)

Stories are **Problem Space** documents. They are vertical feature slices. Do not categorize stories into technical domains (e.g., `gfx`, `network`).

**Story Syntax Requirements:**

* **Goal:** Plain English description of the feature (The "What" and "Why").
* **Scope Boundaries:** Explicit instructions on what *not* to implement to prevent LLM scope creep.
* **Trigger Conditions:** How the user or system invokes the feature.
* **Acceptance Criteria (Definition of Done):** Binary, verifiable facts. (e.g., "A valid JSON file must be created at `~/.config/app/state.json`.")
* **Domain Tags:** Metadata for the Coordinator (e.g., `Tags: core, io, network`).

### 3.2 Requirements (`plan/requirements/[domain]/0000X-req.md`)

Requirements translate the vertical Story into categorized **Problem Space** rules.

* A single story will spawn multiple requirement files across different domains (e.g., one in `network/`, one in `core/`).
* **Syntax:** Markdown lists of logic, constraints, and business rules. No C++ code, no class names. Must include a backlink to the parent Story ID.

### 3.3 Architecture & Headers (`include/[domain]/`)

The Architecture/Header agent translates Requirements directly into the **Solution Space**.

* **Rule:** The C++ header file *is* the architecture definition. Do not write markdown architectural summaries.
* **Action:** The Arch Agent reads the Requirements, ingests existing `.h` files in the domain, and outputs updated/new C++ header files.

### 3.4 Review Feedback (`plan/*-review/0000X-feedback.md`)

When a Review Agent rejects a plan or implementation, it writes a markdown file detailing the exact flaws.

* **Rule:** Focus on actual flaws, compile errors, and missed requirements. Do not nitpick formatting. If it works and is structurally sound, approve it.

## 4. The Testing Guardrails

Testing must be structured to constrain the LLM's implementation agent, not validate its hallucinations.

### 4.1 Shift-Left Integration Tests (`tests/integration/`)

* **Goal:** Interface Contract Enforcement.
* **Timing:** Written *before* the Implementation phase, immediately after the Arch/Header phase.
* **Execution:** These are state-driven, End-to-End tests within the application boundary. They must instantiate concrete classes across domains to ensure the architecture links correctly. The Implementation Agent must write code that satisfies this test.

### 4.2 Sociable Unit Tests (`tests/unit/`)

* **Goal:** Validate units of behavior, not single C++ classes.
* **Rule:** Do not aggressively mock internal collaborators. Instantiate real objects (Detroit/Chicago school).
* **Mocking Boundary:** Only mock true system boundaries: File I/O, OS system calls, Network sockets, and Hardware driver contexts (e.g., isolate C++ rendering logic from actual RTX 5090 Vulkan/CUDA calls using stubs).

---

## 5. Escalation Protocol

There is no omnipotent "Escalation Agent" with global write access. Escalations are handled via a strict **State Reversal Loop**.

1. **Trigger:** A downstream agent (e.g., Implementation) hits an impossible constraint, syntax loop, or architectural flaw.
2. **Report:** The agent halts, writes the exact error and proposed fix to `plan/escalations/0000X-error.md`, and exits.
3. **Reversal:** The Coordinator reads the escalation, uses Taskwarrior to mark the current task as `blocked`, and resets the upstream Taskwarrior task (e.g., the Arch phase) back to `implement`.
4. **Recovery:** The Coordinator rolls back the Git branch to the last known good phase and re-triggers the upstream agent, feeding it the escalation report as its primary prompt.
